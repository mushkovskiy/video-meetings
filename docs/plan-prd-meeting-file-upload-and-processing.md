# Plan: Загрузка записи встречи и её транскрипция

**PRD:** prd-meeting-file-upload-and-processing.md
**Дата:** 2026-10-03

## Фазы реализации

### Фаза 1: Backend — загрузка и хранение записи (Tracer Bullet)

**Цель:** Через API можно прикрепить файл записи к встрече и получить его метаданные и статус. Это минимальный сквозной путь: запрос → валидация → файл на диске → запись в БД → ответ.
**Затрагивает:** backend / database
**Задачи:**

- [ ] Описать хранение записи встречи: имя файла, размер, MIME-тип, дата загрузки, путь к файлу, статус (`processing` / `done` / `failed`), транскрипция. Хранить только метаданные, сам файл кладётся в `UPLOAD_DIRECTORY`, а не в документ MongoDB.
- [ ] `POST /meetings/:meetingId/recording` (multipart): принимает mp3 / wav / m4a / mp4 / webm до 100 МБ, сохраняет файл, ставит статус `processing`. При превышении размера отвечает `413`, при неподдерживаемом формате — `400` с понятным сообщением.
- [ ] `GET /meetings/:meetingId/recording`: возвращает метаданные и статус записи, `404`, если записи нет.
- [ ] Оба эндпоинта проверяют доступ так же, как `GET /meetings/:id`: `401` без токена, `400` на некорректный id, `404` для несуществующей встречи, `403` для чужой.
- [ ] e2e-тесты (Vitest + supertest): успешная загрузка каждого формата, `413` на файл > 100 МБ, `400` на `.pdf`, `401` / `403` / `404` для обоих эндпоинтов, чтение метаданных после загрузки. Обновить `apps/backend/CLAUDE.md` и добавить `http/meetings-recording.http`.

**Когда готова:** `pnpm --filter backend test` зелёный. Файл, загруженный через `http/meetings-recording.http`, лежит в `UPLOAD_DIRECTORY`, а `GET .../recording` возвращает его метаданные со статусом `processing`.

### Фаза 2: Frontend — страница встречи и загрузка файла

**Цель:** Пользователь открывает встречу из дашборда, загружает запись и видит её метаданные и статус.
**Затрагивает:** frontend
**Задачи:**

- [ ] Страница `/meetings/[meetingId]` с названием, описанием, датой и блоком «Запись». Элемент списка встреч на дашборде ведёт на неё.
- [ ] Выбор файла в блоке «Запись» с клиентской проверкой формата (mp3 / wav / m4a / mp4 / webm) и размера (≤ 100 МБ). Неподходящий файл не отправляется, пользователь видит причину отказа.
- [ ] Загрузка с прогрессом в процентах (статус «Загружается»). После неё отображаются имя файла, размер, дата загрузки и статус «В обработке». Ошибки сервера (`413`, `400`, `403`) показываются сообщением.
- [ ] При открытии и перезагрузке страницы существующая запись подтягивается через `GET .../recording` и отображается с актуальным статусом.
- [ ] Playwright e2e: переход с дашборда на встречу, отказ на неподдерживаемый формат, загрузка валидного файла, отображение метаданных и статуса после перезагрузки. Затем проверка через Playwright MCP и skill `ui-ux-pro-max`, все замечания исправлены.

**Когда готова:** `pnpm --filter frontend test:e2e` зелёный. В браузере можно открыть встречу, загрузить запись и увидеть «В обработке» с метаданными, в том числе после перезагрузки.

### Фаза 3: Backend — асинхронная транскрипция

**Цель:** Загруженная запись автоматически расшифровывается в фоне, результат и статус доступны через API.
**Затрагивает:** backend / database
**Задачи:**

- [ ] Сервис транскрипции за интерфейсом (DI-токен в `Component`). Реальная реализация вызывает выбранный внешний сервис или модель, ключи доступа берутся через `Config` и документируются в `.env.example`.
- [ ] После успешной загрузки запускать транскрипцию асинхронно, не блокируя ответ `POST .../recording`.
- [ ] По завершении сохранять текст и ставить статус `done`. При ошибке или недоступности сервиса ставить `failed` и логировать причину через `Logger`.
- [ ] `GET .../recording` возвращает текст транскрипции при статусе `done` и прежние проверки доступа (`401` / `403` / `404`) распространяются на транскрипцию.
- [ ] e2e-тесты с фейковой реализацией сервиса транскрипции: переход `processing → done` с текстом в ответе, переход `processing → failed`, `403` на чтение транскрипции чужой встречи.

**Когда готова:** `pnpm --filter backend test` зелёный. Реальный файл, загруженный через `.http`, через некоторое время отдаёт статус `done` и текст транскрипции.

### Фаза 4: Frontend — отображение транскрипции и статусов обработки

**Цель:** Пользователь видит, как статус меняется сам, и читает транскрипцию на странице встречи. При ошибке может загрузить файл заново.
**Затрагивает:** frontend
**Задачи:**

- [ ] Пока статус «В обработке», страница сама обновляет его без перезагрузки и прекращает опрос на `done` / `failed`.
- [ ] При статусе «Готово» показывать текст транскрипции в блоке «Запись», в том числе после перезагрузки страницы.
- [ ] При статусе «Ошибка» показывать сообщение и давать загрузить файл заново.
- [ ] Playwright e2e (ответы API замоканы): переход «В обработке → Готово» без перезагрузки с появлением текста, состояние «Ошибка» с доступной повторной загрузкой. Затем проверка через Playwright MCP и skill `ui-ux-pro-max`, все замечания исправлены.

**Когда готова:** `pnpm --filter frontend test:e2e` зелёный. В браузере после загрузки файла транскрипция появляется без перезагрузки страницы.

### Фаза 5: Backend — замена записи

**Цель:** Повторная загрузка во встречу с существующей записью полностью заменяет старую.
**Затрагивает:** backend / database
**Задачи:**

- [ ] `POST .../recording` при существующей записи удаляет старый файл с диска и его транскрипцию, затем сохраняет новый файл и запускает обработку с нуля.
- [ ] Результат транскрипции старого файла, завершившейся после замены, не перезаписывает данные новой записи.
- [ ] e2e-тесты: после замены `GET .../recording` отдаёт метаданные нового файла без старой транскрипции, старого файла нет на диске, поздний результат старой транскрипции игнорируется (через фейковый сервис). Обновить `apps/backend/CLAUDE.md` и `.http`.

**Когда готова:** `pnpm --filter backend test` зелёный. Повторная загрузка через `.http` заменяет файл, старые данные недоступны.

### Фаза 6: Frontend — замена записи с подтверждением

**Цель:** Пользователь может заменить запись, но только после явного подтверждения.
**Затрагивает:** frontend
**Задачи:**

- [ ] При существующей записи выбор нового файла открывает диалог подтверждения с предупреждением, что старый файл и транскрипция будут удалены.
- [ ] После подтверждения новый файл загружается и отображается со статусом «В обработке», старая транскрипция исчезает. При отмене ничего не меняется.
- [ ] Playwright e2e: отмена замены оставляет старую запись, подтверждение заменяет метаданные и убирает старую транскрипцию. Затем проверка через Playwright MCP и skill `ui-ux-pro-max`, все замечания исправлены.

**Когда готова:** `pnpm --filter frontend test:e2e` зелёный. В браузере замена записи работает только после подтверждения.
